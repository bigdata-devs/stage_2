\section{Introduction and Objectives}
\label{sec:introduction}

Stage~1 built the data layer of the search engine and measured it: four
behaviourally identical implementations of the same pipeline were compared on
one host, and the group selected \textbf{Go}, the \textbf{batch-based
datalake} and the \textbf{MongoDB inverted index} for Stage~2. The selection
of MongoDB was explicitly provisional. It did not rest on the Stage~1
measurements, where file-based indexes answered queries faster, but on a
requirement those measurements could not cover: several independent processes
reading and updating one shared index. The Stage~1 report therefore left
Stage~2 a concrete obligation, namely to measure MongoDB under concurrent
access before confirming the choice.

Stage~2 turns that data layer into a \emph{service-oriented architecture}
(SOA). The monolithic pipeline is decomposed into three autonomous processes
(the Ingestion, Indexing and Search services) that cooperate through REST
interfaces with JSON payloads, an explicit coordination mechanism decides which
work is ready and when its result may be published, and every process
(replicas, the reverse proxy, the database server and the coordinator) runs on
a single host. The objectives of this stage, and where this report shows that
each was met, are the following:

\begin{enumerate}[label=\textbf{O\arabic*}, leftmargin=2.2em]
  \item \textbf{Decomposition.} Separate ingestion, indexing and search into
  independently deployable services with their own REST APIs and internal data
  model (\cref{sec:architecture,sec:implementation}).
  \item \textbf{Explicit coordination.} Guarantee that a book is indexed only
  after its ingestion has completed, that search reads only published data,
  and that repeated or concurrent requests never duplicate or corrupt records.
  The design combines classical orchestration by a Control Module with
  persistent completion markers, a publication state in the datamart and a
  cross-replica lease (\cref{sec:coordination,sec:decision-coordination}).
  \item \textbf{Contracts.} Distinguish the front-end-facing API from the
  internal and operational interfaces, publish versioned OpenAPI
  specifications and validate the running services against them
  (\cref{sec:api}).
  \item \textbf{Concurrency.} Serve many concurrent users and account for the
  three levels of concurrency the assignment separates: client concurrency,
  process replicas and threads within a process
  (\cref{sec:replicas-threads,sec:decision-concurrency}).
  \item \textbf{Measurement.} Quantify indexing throughput, query latency,
  CPU and memory per process and for the host, the effect of replication and
  threading, and the coordination overhead, and locate the limits of the
  single-machine deployment (\cref{sec:benchmarks}).
  \item \textbf{Preparation for Stage 3.} Identify every assumption that only
  holds on one machine and describe how the architecture will evolve into a
  cluster (\cref{sec:conclusions}).
\end{enumerate}

\begin{keyresults}[Key results]
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Contracts hold.} The running stack passes \fixed{19} of
  \fixed{19} checks of the API validation script, \fixed{365} automated Go
  tests pass against a live MongoDB server with none skipped, and both
  end-to-end scripts pass.
  \item \textbf{Search saturates at about 250~req/s.} From \fixed{10}
  concurrent clients onwards throughput stays at 246--250~req/s, and mean
  latency grows linearly with concurrency as Little's law predicts (within
  2\%); the 95th percentile reaches 674~ms at \fixed{100} clients, above the
  500~ms objective.
  \item \textbf{MongoDB is the first bottleneck.} \code{mongod} consumes 9.2 to
  11.0 of the host's 12 logical CPUs, about 44~ms of CPU per query, while each
  Search process needs about 1~ms of CPU per query and less than 23~MiB of
  memory.
  \item \textbf{A second Search replica does not raise the ceiling.} With two
  replicas behind nginx, throughput changes by $-1.8\%$ to $+4.0\%$ and the
  95th percentile by $-4.6\%$ to $+3.1\%$ with no consistent sign: the
  replicas share the saturated datamart and the same CPU.
  \item \textbf{Indexing scales sub-linearly.} One to ten concurrent updates
  raise throughput from 1.10 to 5.33~books/s (48\% parallel efficiency) while
  the MongoDB CPU cost per book grows from 0.87 to 1.37 core-seconds,
  evidence of write contention inside the datamart.
\end{itemize}
\end{keyresults}

\paragraph{Scope of the claims.}
Every performance statement in this report refers to the host described in
\cref{tab:host} (one laptop-class machine running Docker under WSL2), to the
datasets of \cref{tab:workloads} (a datamart of \fixed{300} published books for
search, a corpus of \fixed{20} books for indexing) and to one run per
configuration. The numbers characterise this implementation on this machine.
Following the assignment, a single-machine experiment is \emph{not} presented
as evidence of cluster scalability; that question belongs to Stage~3.
Section numbers follow the report structure of the assignment, in which item~1
is the cover page.

Provider of the \route{/ingest} API. For a book ID it downloads the plain-text
edition from Project Gutenberg, splits it at the official
\code{*** START/END OF THE PROJECT GUTENBERG EBOOK} markers and stores the
licence header and the body as two files in the batch-based datalake chosen in
Stage~1. A book is reported as stored only when both files are complete.

\paragraph{Indexing Service.}
Provider of the \route{/index} API. It reads a complete book from the
datalake, extracts its metadata (title, author, ISO~639 language codes,
publication and release years) and its normalised body terms, and writes both
into the MongoDB datamart: one metadata record per book and one posting list
per term. It also rebuilds the whole datamart from the datalake and reports
indexing statistics.

\paragraph{Search Service.}
Provider of the front-end API. It validates keyword queries, normalises them
with the same tokenizer the Indexing Service applies to book bodies, and
answers each query with a single server-side aggregation over the datamart
that intersects the posting lists, joins published metadata, applies the
optional filters, counts every match and returns one ranked page. It is
stateless, which is what allows it to run as several replicas behind nginx.

\subsection{Coordination mechanism}
\label{sec:coordination}

The architecture uses \textbf{classical orchestration} (the design of Figure~1
of the assignment), reinforced by three shared-state mechanisms that make the
workflow safe across process restarts and replicas:

\begin{enumerate}
  \item \textbf{Orchestration.} The Control Module decides \emph{which} work
  is ready and \emph{who} performs it. Each candidate book is handed to
  exactly one worker of the run, which calls the Ingestion Service and, only
  after a successful answer, the Indexing Service. Both calls are synchronous:
  a \code{2xx} answer means the step has \emph{completed}.
  \item \textbf{Persistent completion markers.} Completion is recorded where
  it happens. In the datalake, a book exists only when both of its files
  exist, and the header is written last. In the control state, the Control
  Module appends each book ID to \code{downloaded\_books.txt} or
  \code{indexed\_books.txt} after the corresponding step succeeds, and to
  \code{failed\_books.txt} with a reason when it gives up.
  \item \textbf{Publication state in the datamart.} Each metadata record
  carries a \code{status} that is \code{pending} while its postings are being
  written and \code{published} once they are complete. The Search Service
  only ever returns published books, so a half-indexed book is invisible.
  \item \textbf{Cross-replica lease.} A full rebuild must not run twice at
  the same time. A lease document in MongoDB serialises rebuilds across every
  Indexing replica that shares the datamart.
\end{enumerate}

\Cref{fig:lifecycle} traces one book through this workflow. The dependency
required by the assignment (a book becomes eligible for indexing only after
its ingestion has completed) is enforced twice: by the orchestrator, which
only calls \route{POST /index/update/\{id\}} after ingestion returned
\code{2xx}, and by the Indexing Service itself, which answers
\code{404 book\_not\_found} for a book whose two datalake files are not both
present. Search reads a consistent published state because publication is the
last write of every update, and because a rebuild builds new collections aside
and swaps them in with an atomic rename. If a process stops between completing
an operation and recording it, the book is simply not recorded; the next run
replays the call, and because every service operation is idempotent the replay
converges to the same state without duplicates (\cref{sec:readiness}).

\paragraph{Failure semantics.}
The orchestrator classifies every failed step. Network errors, timeouts,
HTTP \code{408}, \code{429} and \code{5xx}, and \code{failed} status answers
are \emph{transient}: the step is retried up to three times with a backoff that
starts at 1~s and doubles. Any other \code{4xx} answer and an \code{unavailable}
status are \emph{permanent}: the book is recorded in \code{failed\_books.txt}
and skipped by later runs unless the operator re-enqueues it with
\code{-retry-failed}. A book interrupted by \code{SIGINT} or \code{SIGTERM} is
left pending and claimed again by the next run.

activities one process executes). \Cref{fig:concurrency} maps them onto the
two request paths of the system.

\paragraph{Distribution of requests among replicas.}
nginx resolves the compose service name \code{search} through Docker's
embedded DNS every 5~s and balances requests with \code{least\_conn}, so each
request goes to the replica with the fewest requests in flight. This policy
suits a workload whose cost varies with the posting-list length of the query,
where strict rotation could queue a cheap query behind an expensive one.
Scaling to $R$ replicas needs no proxy restart.

\paragraph{Threads inside a process.}
Every service is a Go process whose HTTP server starts one goroutine per
connection. Goroutines blocked on network input or output (a MongoDB round
trip, a Gutenberg download) are parked by the runtime's network poller and do
not hold an operating-system thread: during the benchmark each Search process
served up to 100 concurrent requests with 13 to 24 operating-system threads
(\code{PIDs} column of \code{docker stats}). Concurrency that would overload a
shared resource is bounded explicitly with buffered channels used as
semaphores: eight concurrent downloads in the Ingestion Service, eight
concurrent index updates in the Indexing Service, and $W$ workers in the
Control Module. Shared in-process state is protected by mutexes, as detailed
in \cref{sec:decision-concurrency}.

\paragraph{Concurrent access to shared storage.}
Separate processes never share memory; they share the datalake volume, the
MongoDB server and the control-state volume, each with its own cross-process
rule. Datalake files are replaced atomically (temporary file, \code{fsync},
rename), so a reader sees either no file or a complete one. MongoDB applies each
document update atomically, and the write path is idempotent, so concurrent
updates of the same book converge. Control-state files are appended under an
exclusive \code{flock} (\code{LockFileEx} on Windows), so concurrent writers
never interleave partial lines.

\paragraph{Datalake.}

the header, so the presence of both files is the completion marker that every
reader checks.

benchmarks) holds three collections, described in \cref{tab:collections}. Both

needs no manual set-up.

\subsection{Single-host deployment}
\label{sec:deployment}

The whole system is described by one \code{docker-compose.yml} (project
\code{boogle-engine}): \code{mongo} (\code{mongo:7}), \code{ingestion},
\code{indexing}, \code{search} (with \code{replicas: \$\{SEARCH\_REPLICAS:-1\}}),
\code{nginx} (\code{nginx:1.28-alpine}) and the Control Module under the
\code{tools} profile, started on demand with
\code{docker compose --profile tools run --rm control -discover}. A single
multi-stage \code{Dockerfile} builds the four Go binaries statically
(\code{golang:1.25-alpine} builder, \code{CGO\_ENABLED=0}) into
\code{alpine:3.21} images that run as an unprivileged user. Containers carry
code only: the datalake, the control state and the datamart live in named
volumes, so recreating a container never loses pipeline state. Services reach
one another by compose service name (\code{http://ingestion:7001},
\code{mongodb://mongo:27017}); host ports come from \code{.env}
(\code{INGESTION\_PORT}, \code{INDEXING\_PORT}, \code{SEARCH\_PORT},
\code{MONGO\_PORT}). Health checks gate the start-up order: the Indexing and
Search services wait for a healthy MongoDB, nginx for a healthy Search replica,
and the Control Module for healthy Ingestion and Indexing services.

Every process, including the MongoDB server, the reverse proxy and, during
the benchmarks, the k6 load generator and the resource sampler, runs on the
one host described in \cref{tab:host}. No container had CPU or memory limits in
the official session (the limits in \code{docker-compose.yml} are commented
out), so all processes competed for the same 12 logical CPUs and 9.7~GiB of
memory.

\section{API Design and Contracts}

\subsection{Consumers and use cases}
\label{sec:use-cases}

The interfaces serve three kinds of consumer, and the contract of each is
specified separately:

\begin{itemize}
  \item \textbf{The front-end} (a browser application, or an HTTP client such
  as k6 or \code{curl} exercising the same contract during Stage~2). Its use
  cases are \emph{UC1}, searching books by one or more keywords with optional
  author, language and publication-year filters and paginated results;
  \emph{UC2}, opening the detail page of one book; and \emph{UC3}, populating
  the filter controls with the values that actually occur in the catalogue.
  \item \textbf{The Control Module}, which consumes the internal APIs to ingest
  a book (\emph{UC4}), check that a book is complete in the datalake
  (\emph{UC5}), discover the books already stored (\emph{UC6}), index and
  publish a book (\emph{UC7}) and, as an administrative operation, rebuild the
  whole datamart (\emph{UC8}).
  \item \textbf{Operational components}: Docker health checks, the readiness
  probe of the Control Module, the corpus guard of the load benchmarks and the
  developers who browse the interactive documentation (\emph{UC9}).
\end{itemize}

The front-end never reads files, never connects to MongoDB and does not need
to know how the services are coordinated: its contract describes application
data only. Ingestion commands, index rebuilds and datalake paths are internal
concerns and do not appear in it.

\subsection{Front-end contract}
\label{sec:frontend-contract}

\paragraph{GET /search.}
The required search operation and all its filter combinations are variants of
this single endpoint. \Cref{tab:search-params} specifies its parameters.
Several design rules complete the contract.

\begin{itemize}
  \item \textbf{Term semantics.} \code{q} is split exactly like book text:
  runs of the letters a--z, case-insensitive, so digits, spaces and punctuation
  separate words (\code{Moby-Dick} searches \code{moby} AND \code{dick}).
  Repeated words count once. Stop words (\emph{the}, \emph{and}, \emph{of},
  \ldots), single letters and Roman numerals are never indexed and are
  ignored, so a \code{q} made only of them matches nothing and returns 200 with
  an empty page. A book matches only if it contains \emph{every} remaining
  term (AND). The Search Service reuses the Indexing Service's tokenizer, so a
  query word and a body word always normalise alike.
  \item \textbf{Filters} combine with AND. \code{author} is a case-insensitive
  substring match, \code{language} an exact, case-insensitive ISO~639 code that
  matches any code of a multilingual book (stored as \code{"en,fr"}), and
  \code{year} an exact \code{publication\_year}. Empty filter values are treated
  as absent, and only applied filters are echoed in \code{filters}.
  \item \textbf{Ordering.} Results are ranked by relevance, defined as the sum
  of the query terms' frequencies in the book, in descending order, with ties
  broken by ascending \code{book\_id}, so pagination is deterministic.
  \item \textbf{Pagination.} \code{total} counts every match across all pages,
  whereas \code{results} holds at most \code{limit} books starting at
  \code{offset}. A valid query without matches, or an \code{offset} past the
  last match, returns 200 with \code{results: []} and the true \code{total}.
  \item \textbf{Bounded work.} At most 10 distinct terms and 100 results per
  page are accepted, which bounds the posting lists a single request may
  intersect and the size of each response.
\end{itemize}

\subsection{Internal contracts}
\label{sec:internal-contracts}

The internal operations have no request body; their responses are small
JSON documents. The following exchanges are taken from the committed evidence
(\code{docs/evidence/\allowbreak rebuild\_replica.md} and the service
specifications):

\begin{lstlisting}
POST /ingest/1342           -> 200 {"book_id":1342,"status":"downloaded",
                                    "path":"/data/datalake/batch_1000_1999/1342"}
POST /index/update/1342     -> 200 {"book_id":1342,"index":"updated"}
POST /index/rebuild         -> 200 {"books_processed":383,"elapsed_time":"8m0.945s"}
POST /index/rebuild         -> 409 {"error":"rebuild_in_progress",
   (lease held elsewhere)           "message":"an index rebuild is already running"}
GET  /index/status          -> 200 {"books_indexed":300,"last_update":"2026-11-01T16:39:23Z",
                                    "index_size_MB":61.1}
\end{lstlisting}

\paragraph{Ingestion.}
\route{POST /ingest/\allowbreak\{book\_id\}} answers \code{downloaded}, or
\code{available} when the book was already complete, in which case nothing is
downloaded. A book that Project Gutenberg does not serve, or whose text lacks
the START/END markers, is \code{404 book\_unavailable}, a permanent outcome. A
transient download failure, or an exhausted ingestion budget (2~minutes by
default, queueing and retries included), is \code{503 download\_failed}, which
the caller should retry. Concurrent requests for the same book join one shared
download, so the endpoint is safe under duplicate submissions.

\paragraph{Indexing.}
\route{POST /index/update/\allowbreak\{book\_id\}} answers \code{updated} once the
book's metadata and postings are in the \emph{published} index, visible to every
request that starts afterwards. Re-indexing replaces the book's metadata record
and its postings, including the removal of terms the new version no longer
contains, so the index ends up exactly as after the first call. If a rebuild is
running, the update is not blocked: it is recorded and replayed on the rebuilt
index right after the swap. \route{POST /index/rebuild} builds a new catalogue
and index aside and publishes them in one step (the 383-book figure above is
the run of \cref{sec:bench-indexing}); it answers \code{409
rebuild\_in\_progress} while another replica holds the rebuild lease and
\code{503 rebuild\_interrupted} if its budget (10~minutes by default) runs out,
in which case the previous index stays published. \route{GET /index/status}
reports the published books, the time of the last change and the document
bytes of the datamart (\code{dbStats.dataSize}).

\paragraph{Timeouts and retries expected of the caller.}
The specification states, per operation, the timeout and failure behaviour
expected of the caller, and the Control Module implements it. A call to
\route{POST /ingest} may take up to 150~s, above the service's own 2-minute
budget, so the service always answers before the caller gives up. Indexing,
status and readiness calls are bounded at 30~s. Transient failures (transport
errors, timeouts, \code{408}, \code{429}, \code{5xx}) are retried three times
with a doubling backoff that starts at 1~s, while permanent ones (other
\code{4xx}) are recorded once and not retried. A client that disconnects
cancels only its own index update, because the request context is propagated
down to the MongoDB writes, whereas a shared download continues for the other
callers that joined it.

\subsection{Exposure and cross-origin access}
\label{sec:cors}

The front-end reaches the Search API through a single entry point, nginx on
port 7003, whatever the number of replicas. A browser front-end served from
another origin (for example a development server on \code{localhost:5173})
needs CORS, which the Search Service implements as middleware around every
route. The allowed origins come from \code{CORS\_ALLOWED\_ORIGIN}: \code{*} by
default, which is safe for a public, read-only API that uses no credentials,
or an explicit comma-separated list, in which case every response also carries
\code{Vary: Origin}. A preflight from an allowed origin is answered with
\code{204} and \code{Access-Control-Allow-Methods: GET, HEAD, OPTIONS},
\code{Access-Control-Allow-Headers: Content-Type} and
\code{Access-Control-Max-Age: 600}; a preflight from any other origin receives
\code{403 origin\_not\_allowed}. Credentials are never allowed, and a value that
names no valid origin stops the service at start-up instead of silently
blocking the front-end. In Stage~2 the internal ports 7001 and 7002 are also
published on the host, for the Control Module and the Swagger pages; the
front-end contract never uses them.

\subsection{Technology stack and code organisation}
\label{sec:stack}

The assignment's reference template is a Java~17 service built with Javalin,
Gson and Maven and benchmarked with JMH. The group implemented the services in
\textbf{Go} instead, as selected and justified by the Stage~1 measurements
(highest datalake write throughput of the four implementations compared, and
fastest index builds from 500 books upward). Each element of the template has a direct
counterpart:

\begin{itemize}
  \item \textbf{HTTP server and router} (Javalin): the standard library
  \code{net/http} server with the method-aware \code{http.ServeMux} introduced
  in Go~1.22. Routes are declared as patterns such as
  \code{"POST /index/update/\allowbreak\{book\_id\}"}, path parameters are read with
  \code{Request.PathValue}, and a request with another method on a declared
  path is answered with \code{405} automatically. No third-party router or web
  framework is used.
  \item \textbf{JSON serialisation} (Gson): \code{encoding/json}, with response
  types declared as Go structs whose tags fix the field names of the contract.
  \item \textbf{Build} (Maven): one Go module (\code{boogle-engine}, Go~1.25)
  with four entry points under \code{cmd/}; \code{go build} produces one static
  binary per service, and the multi-stage \code{Dockerfile} packages them.
  \item \textbf{Micro-benchmarks} (JMH): Go's \code{testing.B} framework, with
  adaptive iteration counts, ten samples per benchmark and aggregation by
  \code{benchstat} (medians with 95\% confidence intervals, bytes and
  allocations per operation), kept in \code{\_test.go} files and therefore
  excluded from the service binaries.
  \item \textbf{Datamart access}: the official MongoDB Go driver
  (\code{go.mongodb.org/\allowbreak mongo-driver/v2}, v2.9.2); \textbf{API
  documentation}: \code{swaggo/swag} and \code{http-swagger}; \textbf{logging}:
  the structured \code{log/slog} logger.
\end{itemize}

\Cref{tab:layout} summarises the repository. The Go code follows a
\textbf{hexagonal (ports and adapters) structure}. Each use case lives in a
\emph{core} package (\code{internal/ingestion}, \code{internal/indexing},
\code{internal/search}, \code{internal/control}) that declares, as Go
interfaces, both the operations it offers and the operations it needs from
outside. \emph{Adapters} connect the cores to a technology: the HTTP handlers
call a core through its \emph{driving} ports (\code{BookIngester},
\code{BookIndex}, \code{Searcher}), while MongoDB, the datalake, the Gutenberg
client, the HTTP clients of the Control Module and the control-state files
implement its \emph{driven} ports (for example \code{indexing.IndexWriter} or
\code{search.Index}). Source dependencies point only into the core: no core
package imports HTTP, MongoDB or filesystem code, and every adapter asserts at
compile time the ports it implements. The use cases are therefore tested with
in-memory fakes, and moving a store to Stage~3 infrastructure means writing a
new adapter rather than changing a service. The services share one skeleton:
\code{main}, the composition root, parses flags and environment variables,
builds the adapters and injects them into the core constructors (constructor
injection), mounts the handlers on a \code{ServeMux}, starts an
\code{http.Server} whose read, header, write and idle timeouts are bounded, and
shuts down gracefully on \code{SIGINT} or \code{SIGTERM} (30~s grace for
Ingestion and Indexing, 10~s for Search). Test fakes live in \code{\_test.go}
files and are never compiled into a service binary.

\subsection{Ingestion Service}
\label{sec:impl-ingestion}

A request for \route{POST /ingest/\allowbreak\{book\_id\}} flows from the handler into
the \textbf{ingestion core} (\code{ingestion.Service}) and from there to two
driven adapters. The core implements single-flight per book: concurrent
requests for the same ID join one shared ingestion, tracked in an in-flight map
guarded by a mutex. Each ingestion runs detached from the requests that wait
for it, under its own 2-minute budget (\code{-ingest-timeout}), so a caller
that disconnects cancels neither the shared work nor the other callers. The
core first checks the datalake and answers \code{available} without
downloading when the book is already complete. Otherwise it waits for one of
eight download slots (\code{-workers}), a buffered channel, and the
\textbf{Gutenberg client} downloads
\code{https://www.gutenberg.org/\allowbreak cache/epub/<id>/pg<id>.txt} through one shared
\code{http.Client} with connection reuse (30~s per attempt); the core makes up
to three attempts with a 1~s doubling backoff and retries only the errors the
client classifies as transient. The
\textbf{splitter} then separates header and body at the START/END markers;
a missing marker makes the book \code{unavailable}. Finally the
\textbf{datalake} stores the body and then the header, each through a
temporary file in the same directory, \code{fsync} and rename. Readiness
follows directly: \route{GET /ingest/status/\{id\}} and \route{GET /ingest/list}
report a book only when both files are present, and a crash at any point
leaves at most a stray temporary file, never a truncated book.

\subsection{Indexing Service}
\label{sec:impl-indexing}

\paragraph{One update.}
\route{POST /index/update/\allowbreak\{book\_id\}} first acquires one of eight update slots
(\code{-max-concurrent-updates}); a request that finds them all busy waits
until a slot frees or its caller disconnects, so a burst of updates cannot
exhaust the datamart connection pool. The \textbf{indexing core}
(\code{indexing.Service}) then reads the book from the datalake through its
\code{BookSource} port (\code{404} if incomplete), extracts the metadata from the header
(title, author, language mapped to ISO~639 codes, original publication year
falling back to the Gutenberg release year), and turns the body into terms
with the Stage~1 tokenizer: lower-casing, keeping the maximal runs of the
letters a--z, and dropping stop words, single letters and Roman numerals. The MongoDB writer,
which implements the core's \code{IndexWriter} port, stores the book in four
ordered, idempotent steps (\cref{fig:lifecycle}):

\begin{enumerate}
  \item replace the book's metadata record with \code{status: pending};
  \item remove the book from every posting list it appeared in
  (\code{\$pull}, bounded by the multikey index on \code{postings.book\_id}),
  so a re-indexed book forgets terms it no longer contains;
  \item upsert one posting per distinct term in unordered bulk writes of at
  most 1{,}000 operations. Each upsert is an update pipeline that filters out
  any previous entry of the book (\code{\$filter}), appends the fresh
  \code{\{book\_id, tf\}} pair (\code{\$setUnion}) and re-sorts the list by
  book ID (\code{\$sortArray}), so replays converge to the same document;
  \item set \code{status: published}, the moment the book becomes searchable.
\end{enumerate}

\paragraph{Rebuild and publication.}
\route{POST /index/rebuild} first claims the cross-replica lease: a single
document in the \code{locks} collection, claimed with \code{findOneAndUpdate},
valid for 2~minutes and renewed every 30~s by a background goroutine. A
request that finds the lease held receives \code{409}; an expired lease, left
by a replica that crashed mid-rebuild, is taken over. The holder streams the
datalake one book at a time into the temporary collections
\code{books\_rebuild} and \code{inverted\_index\_rebuild}, so its memory does not
grow with the datalake, creates their indexes, and publishes them with two
\code{renameCollection} commands (index first, then books). Search therefore
keeps reading the previous complete datamart until the swap. Updates that
arrive during a rebuild are not blocked: an atomic flag, read \emph{before}
each datamart write, makes the indexing core record the book in a
mutex-protected replay list, and the list is re-applied to the fresh datamart after the swap,
so no concurrent update is lost. Recording before writing guarantees that a
swap can never overtake a book that is still being written.

\paragraph{Status.}
\route{GET /index/status} counts the published books and reads the datamart
size from \code{dbStats}. It never fails: a measurement that cannot be taken
is reported as zero and logged, because the endpoint doubles as a readiness
probe.

\subsection{Search Service}
\label{sec:impl-search}

The handler reads the query string and passes it to the \textbf{search core}
(\code{search.Service}), which validates it (\cref{tab:search-params}) and
splits \code{q} into at most ten distinct normalised terms with the indexer's
tokenizer. When every word of \code{q} is one the index never stores, the core
answers an empty page without querying MongoDB. Otherwise it calls its
\code{Index} port, which the MongoDB adapter implements with \textbf{one
aggregation} on \code{inverted\_index}, so a request costs a single round trip
(keeping matching and ranking in the aggregation is a deliberate choice,
discussed in \cref{sec:decision-storage}):

\begin{enumerate}
  \item \code{\$match} the term documents (\code{\_id \$in} terms) and
  \code{\$unwind} their postings;
  \item \code{\$group} the postings by book, collecting the matched terms and
  summing their frequencies into a score, then keep only the books that
  matched every term (the AND);
  \item \code{\$lookup} each surviving book in \code{books}, requiring
  \code{status: published} and applying the author, language and year filters
  inside the lookup;
  \item \code{\$facet} into a total count and a page sorted by score
  (descending) and book ID (ascending), with \code{\$skip} and \code{\$limit}.
\end{enumerate}

Intersecting the postings before the join means that every additional term
shrinks the join instead of growing it. \route{GET /books/\{id\}} and
\route{GET /search/filters} go through the catalog use case
(\code{search.CatalogService}) and read the same datamart through the same
stateless reader, restricted to published books. The process holds no mutable state
beyond the driver's connection pool, which is why replicas are interchangeable
and why nginx may route any request to any of them. At start-up the service
refuses to run if MongoDB is unreachable (fail fast), instead of answering
\code{500} to every request.

\subsection{Control Module}
\label{sec:impl-control}

The Control Module is a command-line tool (\code{cmd/control}) that selects
candidate books (\code{-ids}, \code{-from}/\code{-to}, or \code{-discover}
from \route{GET /ingest/list}), loads the control state, and refuses to start
unless both services answer their readiness routes within 10~s. A pool of
\code{-workers} goroutines (4 by default) then processes the candidates. A
mutex-protected \textbf{book selector} hands each candidate to exactly one
worker; the worker skips books already indexed or failed, ensures ingestion,
records it, ensures indexing and records it, applying the retry policy of
\cref{sec:coordination} to each step. Two further modes support operations:
\code{-retry-failed} atomically empties \code{failed\_books.txt} and
re-enqueues its books, and \code{-verify} reconciles \code{indexed\_books.txt}
with the datamart through \route{GET /books/\{id\}}. Every finished step is
logged with its duration, and the run summary reports throughput and the time
spent in ingestion and indexing steps, which provides the coordination-cost
measurements of \cref{sec:bench-coordination}.

\subsection{Coordination mechanism}
\label{sec:decision-coordination}

\paragraph{Decision and rationale.}
Classical orchestration makes the one hard dependency of the pipeline explicit
in code rather than emergent from message timing, and its synchronous
completion semantics give the clearest definition of ``done'': the Control
Module records a book as indexed only after the Indexing Service has
\emph{published} it. It adds no infrastructure, which matters on a single
host whose CPU is already the scarce resource (\cref{sec:bench-resources}), and
it concentrates retry and failure policy in one place, where it is logged with
per-step durations. Choreography with a broker was judged premature: it would
add a stateful process, with acknowledgement, redelivery and duplicate-handling
rules to specify, while still requiring idempotent consumers, which our
services already are. Shared memory was rejected because it is unsafe across
containers and, as the assignment notes, must be redesigned for Stage~3 anyway.
Time-based coordination would only add latency on top of the readiness markers
we already need.

\paragraph{Why orchestration alone is not enough.}
An orchestrator coordinates the processes it drives, but other actors also
touch shared data: an operator may call \route{POST /index/rebuild} while the
Control Module indexes, and two Indexing replicas may both receive a rebuild.
Correctness therefore does not rest on the orchestrator alone. The datalake
exposes only complete books, the datamart hides books until they are
published, the rebuild lease serialises rebuilds across processes, and every
operation is idempotent so that any replay is harmless.

\paragraph{Trade-offs accepted.}
The Control Module is a single point of coordination: while it is down, no new
book enters the pipeline, although search keeps serving the published index.
It is stateless across restarts, because its progress lives in the control
files, so a restarted run resumes. Exactly-once claiming holds within one run;
running two Control instances concurrently is excluded by operating procedure
rather than enforced, a limitation addressed in \cref{sec:stage3}. Synchronous
calls hold a worker for the whole duration of an index update (1--7~s in
\cref{sec:bench-coordination}), so the worker count is the throughput knob of
the pipeline.

\subsection{API design}
\label{sec:decision-api}

\begin{itemize}
  \item \textbf{Synchronous, idempotent internal operations.} Ingestion and
  indexing of one book take from milliseconds to a few seconds, well within an
  HTTP timeout, so a synchronous response whose \code{200} means ``completed
  and published'' removes the need for job identifiers and status polling.
  Making every \code{POST} idempotent turns retries after timeouts into a safe
  default instead of a hazard. The one long operation, a full rebuild, stays
  synchronous but is guarded by a lease and a budget, and it can be observed
  through \route{GET /index/status}.
  \item \textbf{One search endpoint.} Filters are optional parameters of
  \route{GET /search}, combined with AND, rather than separate routes, as the
  assignment requires; book details and filter values are separate read-only
  routes because the front-end use cases need them.
  \item \textbf{Bounded requests.} The limits of at most 100 results per page
  and 10 terms per query cap the cost of any single request, which is a
  precondition for predictable latency under concurrency.
  \item \textbf{Offset pagination with deterministic order.} Offset and limit
  are stateless and simple for a front-end. Ties in the relevance score are
  broken by book ID, so pages never overlap. Deep offsets cost the datamart
  work proportional to the offset, a known limit of this scheme
  (\cref{sec:improvements}).
  \item \textbf{One error schema, stable codes.} Machine-readable codes let
  callers distinguish permanent from transient failures without parsing
  messages, which is what the Control Module's retry policy relies on.
  \item \textbf{Specification generated from code.} Annotations live next to
  the handlers and the specification is regenerated with \code{go generate},
  so contract and implementation are reviewed in the same commit; the
  validation script then checks that the running service matches the contract.
\end{itemize}

\subsection{Storage selection}
\label{sec:decision-storage}

\paragraph{Datalake on a shared volume.}
The batch-based layout comes from Stage~1, where it matched the book-based
layout on lookup time with far fewer directories. On one host a named volume is
the simplest shared store, and atomic replacement of files gives crash safety
without a database. Its limitation is locality: the volume exists on one
machine only (\cref{sec:stage3}).

\paragraph{MongoDB as the datamart.}
Stage~1 measured the file-based indexes as faster in a single process but
selected MongoDB for Stage~2 on requirements that a single process could not
exhibit. Stage~2 relies on each of those requirements. Separate processes,
including several Search replicas, share one index over the network instead of
each holding a copy. Per-document atomic updates and idempotent upserts let
concurrent writers converge. A server-side aggregation answers a filtered,
ranked and paginated query, together with its total count, in one round trip.
Secondary indexes back the metadata filters. \code{renameCollection} provides
atomic publication of a rebuild, and \code{findOneAndUpdate} provides a
cross-process lease. The JSON file and folder index of Stage~1 offer none of
these properties: they would require a single writer, file locking across
processes, and an in-memory copy of the index inside every Search replica.

\paragraph{Query evaluation stays inside the datamart.}
In the hexagonal structure (\cref{sec:stack}) the search core decides what a
query means (its terms, filters and page) but not how it is evaluated. Keeping
the AND matching of the terms and the relevance ranking (summed term
frequencies, ties broken by book ID) inside the MongoDB aggregation, behind the
core's \code{Index} port, is a deliberate architectural performance choice
rather than an omission. Evaluated on the server, a query costs one round trip
and returns one page of metadata; evaluated in the Search Service, it would
transfer every posting of every query term on each request, and the posting
list of a common term can span most of the corpus. Intersecting the postings
before the join also keeps the join proportional to the matches. The price is
that these rules belong to the adapter: they are documented as the contract of
the port and pinned by the datamart's integration tests, and any future
\code{Index} adapter, for example one on the (term, book) layout of
\cref{sec:improvements}, must reproduce them.

\paragraph{Costs of the data model.}
Storing one document per term with its whole posting list makes reads simple
but has two costs that the benchmarks expose. The first is \emph{write
amplification}: re-indexing book 1342 rewrites the posting arrays of its 6{,}576
distinct terms twice, once to remove the old entry and once to upsert the new
one. The second is a \emph{size ceiling}: a BSON document is limited to 16~MB, so
the posting list of a very common term would hit the limit at a few hundred
thousand books. The datamart's integration guide (\code{docs/mongodb.md})
proposes the Stage~3 replacement, one document per (term, book) pair, which is
discussed in \cref{sec:improvements}.

\subsection{Concurrency model and protection of shared state}
\label{sec:decision-concurrency}

Go's concurrency model maps naturally onto a request-serving service.
\code{net/http} serves every connection on its own goroutine, and the runtime
multiplexes goroutines onto \code{GOMAXPROCS} operating-system threads (12 on
the benchmark host, the runtime default, which is not overridden). A goroutine
costs a few kilobytes of stack, and one blocked on I/O does not hold a thread,
so concurrency is cheap. The design decisions therefore concern \emph{where to
bound} concurrency and \emph{how to protect} shared state.
\Cref{tab:primitives} lists every synchronisation mechanism, distinguishing
in-process primitives from cross-process ones. As the assignment stresses, an
in-process lock protects the goroutines of its own process only and does not
coordinate separate replicas; wherever replicas must agree (the rebuild), the
agreement is held in MongoDB.

a goroutine indefinitely, and a burst of index updates queues in the handler
instead of opening unbounded connections to MongoDB. The driver's default pool
of at most 100 connections per process is the last bound.

\paragraph{The nginx front door.}
nginx publishes the Search API on a stable port, so clients, k6 and the
validation script use \code{http://localhost:7003} whatever the number of
replicas. Its configuration encodes four further decisions. First,
\code{least\_conn} sends each request to the replica with the fewest requests
in flight, since query costs vary widely. Second, \code{resolve} with a 5~s DNS
validity lets \code{--scale search=N} add or remove replicas without
restarting the proxy. Third, \code{proxy\_next\_upstream error} retries a
request on another replica only when the first cannot be \emph{reached}; slow
answers are never retried, because retrying them would double the load
precisely when the system is saturated. Fourth, the 20~s read timeout exceeds
the replicas' 15~s write timeout, so a slow search fails at the replica, which
logs it, rather than at the proxy. Every response carries an
\code{X-Upstream} header naming the replica that served it, which made the load
split of the replica experiment observable.

\subsection{Where replication and threading help, and where they add contention}
\label{sec:decision-scaling}

The decisions above lead to expectations that \cref{sec:benchmarks} tests:

\begin{itemize}
  \item \textbf{Stateless Search replicas} can be added freely and spread
  requests evenly. They raise throughput only if the Search process itself is
  the bottleneck; if the shared datamart or the host CPU saturates first,
  replicas merely move the same work into more processes, and each replica's
  connection pool adds server threads to an already busy \code{mongod}. On one
  host their certain benefit is availability: nginx routes around a replica
  that stops.
  \item \textbf{Threads for CPU-bound work}, such as tokenisation, metadata
  parsing and header/body splitting, should scale up to the number of physical
  cores (six on this host) and less beyond, where they share cores through
  simultaneous multithreading.
  \item \textbf{Concurrency for network-bound work}, such as downloads from
  Project Gutenberg, should scale almost linearly until the upstream server or
  the network limits it, because waiting goroutines cost no CPU.
  \item \textbf{Concurrent index updates} contend inside MongoDB: books share
  many terms, so concurrent updates rewrite the same term documents. More
  update slots or Indexing replicas would add contention rather than
  throughput, and multiple Indexing replicas would additionally require routing
  updates to the rebuild owner, because the replay list of concurrent updates
  is kept per process.
\end{itemize}

\paragraph{Metrics and measurement rules.}
\emph{Throughput} $X$ is the number of requests completed in a hold phase divided
by its 30~s; for indexing, one successful update indexes one book, so
requests per second equal books per second. \emph{Latency} $R$ is the response
time of every successful request as measured by k6, summarised by mean,
median and the 90th, 95th and 99th percentiles. \emph{CPU} is the
\code{docker stats} value expressed in logical cores (100\% of one core =
1.0), so the host provides 12.0; memory is the container's resident memory.
Resource samples are aligned with the k6 phases through the scenario start
recorded by each run (\code{setup\_data.startedAt}) plus the phase offsets, and
each per-level value averages the 8 to 10 samples that fall inside the hold
window after its first 2~s. Samples outside a run's windows are discarded:
the sampler of the one-replica run kept recording into the first minutes of
the two-replica run, and those rows are not attributed to either
configuration. Every configuration was run once (\cref{sec:validity}).

\paragraph{Analytical lens: operational laws.}
Because the load is a closed system in steady state, three laws of operational
analysis hold for every hold phase without any assumption about service-time
distributions, and they turn the plots below into diagnoses:
\begin{itemize}
  \item \emph{Little's law}, $N = X\,(R + Z)$: with think time $Z = 0$, the mean
  response time must equal $N/X$. A mismatch would reveal failed or
  unaccounted work.
  \item \emph{Utilisation law}, $U_k = X\,D_k$: the busy time of resource $k$
  is the throughput times the \emph{service demand} $D_k$, the resource time one
  request consumes. Dividing the CPU of each container by the throughput
  therefore yields the CPU cost of one request in each process.
  \item \emph{Asymptotic bounds}: $X(N) \le \min\{N/D,\; X_{\max}\}$ and
  $R(N) \ge \max\{D,\; N/X_{\max}\}$, where $D$ is the response time of a lone
  request and $X_{\max} = m / D_{\text{cpu}}$ is the capacity of the bottleneck
  ($m$ processors, $D_{\text{cpu}}$ CPU seconds per request). The two bounds meet at
  the \emph{knee} $N^{*} = X_{\max} D$, the concurrency beyond which extra
  clients can only queue.
\end{itemize}

\paragraph{Sub-linear scaling.}
Ten concurrent updates index 5.33~books/s, $4.85\times$ the single-client rate
of 1.10~books/s, so parallel efficiency falls from 65\% at five clients to
48\% at ten (\cref{fig:indexing}a). The gap to linear scaling is not lost work:
all 423 timed updates succeeded, and the mean latency of every level agrees
with Little's law, $R = N/X$ (0.91, 1.39 and 1.88~s predicted against 0.92,
1.37 and 1.90~s measured). The extra latency is therefore time spent waiting
or contending. Part of it is designed: at ten clients the handler admits eight
updates and the other two wait for a slot.

\paragraph{Contention, not capacity.}
A capacity limit and a contention limit look alike on a throughput curve, but
the utilisation law separates them. If indexing were capacity-bound, the CPU
cost of a book would stay constant and throughput would stop only when the
host ran out of CPU. Neither happens. At ten clients the stack uses 8.15 of
the 12 logical CPUs (68\%), yet throughput has already flattened; and the cost
of a book is not constant but rises from 1.02 to 1.53 core-seconds
(\cref{fig:indexing}b). All of that growth is inside \code{mongod}, whose cost
per book grows by 47\% at five clients and 58\% at ten, while the Indexing
Service spends a flat 0.15--0.16 core-seconds per book on reading, tokenising
and encoding the writes. Measured against the single-client cost, about one
core-second in three that the stack consumes at ten clients is overhead of
concurrency: at the single-client cost, the same 8.15 cores would have indexed
8.0~books/s instead of 5.33.

The mechanism is the shape of the write. Each update rewrites one posting
array per distinct term twice (the \code{\$pull} of the old entry and the upsert
pipeline), several thousand documents per book, and the books of the corpus
share most of their common terms, so concurrent updates write the same term
documents. Serialised document writes and retried write conflicts inside the
storage engine are consistent with a per-book cost that grows with
concurrency. This attribution remains a hypothesis: the server's conflict and
lock counters (\code{serverStatus}) were not recorded.

\paragraph{The write path in isolation.}
The micro-benchmark \code{IndexBookRealBook} re-indexes book 1342 through the
real write path on an otherwise empty datamart: 636.9~ms per book ($\pm$2\%,
95\% confidence), for 6{,}576 distinct terms and 58{,}860 tokens, with 42.4~MiB
and 444{,}400 allocations per call on the client side. Because every posting
array holds a single entry in this benchmark, its cost is the per-term overhead
of the update pipeline, not the length of the lists. Tokenising a book costs
13.7~ms on one thread (\cref{tab:micro}), about 2\% of the write. Indexing time
is therefore dominated by datamart writes, and tokenising faster would not
help.

\paragraph{Full rebuild.}
In the rebuild-lease experiment, replica A rebuilt the 383-book datalake in
8~min 0.9~s (0.80~books/s through the single-writer rebuild path). Replica B's
overlapping request was answered \code{409 rebuild\_in\_progress} in under a
second, and its retry after the lease was released succeeded in 7~min 54.5~s
(0.81~books/s). \Cref{tab:indexing-summary} collects every indexing throughput
measured.

\paragraph{Saturation happens at about six clients.}
One client obtains 47.2~req/s; ten obtain 246~req/s, only $5.2\times$ more;
50 and 100 clients obtain no more at all (246--250~req/s). The bounds of
\cref{fig:search}a locate the transition without fitting anything. A lone query
takes $D = 21.2$~ms, so with no queueing $N$ clients could push $N/D =
47.2\,N$~req/s. One query consumes 45.2 core-milliseconds of server CPU at
saturation, so the 12 logical CPUs cap throughput at $X_{\max} = 265$~req/s. The
two bounds meet at $N^{*} = X_{\max} D \approx 5.6$ clients: below that
concurrency a client rarely waits, above it every additional client only
lengthens the queue. The measured plateau reaches 93--94\% of $X_{\max}$, and the
remaining CPU went to the load generator, the Docker daemon and WSL2, which
were not sampled. The knee lies close to the six physical cores of the host,
as expected when a query keeps one core busy for practically its whole lifetime
(\cref{sec:bench-resources}): about six aggregations can progress at full speed
at once, and a seventh has to share a core.

\paragraph{Latency past the knee is pure queueing.}
Above $N^{*}$, the mean grows linearly with the number of clients, from 40~ms at
10 clients to 202~ms at 50 and 400~ms at 100 (\cref{fig:search}b). Two checks
show that the system behaves as one clean bottleneck. First, the means agree with
Little's law to within 2\% at every level (\cref{tab:search}), so no work is
lost or hidden. Second, they stay 6--7\% above the asymptotic lower bound
$N/X_{\max}$, and that gap is constant: throughput does not fall as the queue
grows, so there is no thrashing, lock convoy or retry storm, only waiting. The
tail widens with the queue: the 95th percentile is 1.44 to 1.63 times the
median and the 99th 1.62 to 1.89 times, because a query that lands behind a
long aggregation waits for it.

\paragraph{Service objectives.}
The script's objectives are a mean below 200~ms over the whole run and a 95th
percentile below 500~ms at every level. The first holds (194.0 and 195.8~ms
over the two runs). The second holds up to 50 clients (345 and 356~ms) and
fails at 100 (674 and 680~ms), which is why k6 exits with code 99; every
availability threshold (fewer than 1\% failed requests, more than 99\% passed
checks) passed. With zero think time the benchmark is deliberately harsher
than real traffic. Little's law with a think time $Z$ between a user's
searches gives the population a saturated service supports:
$N \approx X\,(R + Z) \approx 1{,}250$ users who search every 5~s. This is an
estimate derived from the law, not a measurement.

\paragraph{The datamart consumes the host.}
With one client, \code{mongod} already uses one full core, and its 20.8~ms of

one core for practically the whole request. From 10 clients onwards

engine, in terms of where the cycles go, is the aggregation inside MongoDB.

\paragraph{Why the cost of a query doubles under load.}
The CPU cost of one query is not constant: it rises from 20.8 core-ms with one
client to 37.6 with ten and 44.4 with fifty (\cref{fig:cpu}c), a factor of 2.1.
Between 10 and 50 clients \code{mongod} received 1.7 more cores but served no
more queries. The factor of about two is the signature of simultaneous
multithreading: the host has six physical cores presented as 12 logical CPUs,
and once more aggregations are runnable than there are physical cores, two
hardware threads share the execution units of one core, each progressing at
roughly half speed while \code{docker stats} charges both as busy. The
consistent arithmetic is that six physical cores running one aggregation each at
the single-client cost would deliver $6 / 20.8~\text{ms} \approx 290$~req/s; the
measured plateau is 86\% of that, a gap compatible with a lower all-core clock
than the single-core turbo and with the CPU taken by k6. Clock frequency and
hardware counters were not recorded, so this mechanism is a well-supported
hypothesis rather than a measurement. Its practical reading matters more than
its proof: on this host, \emph{logical} CPUs are not capacity, and the
effective processor count for aggregation-heavy work is closer to six than to
twelve.

\paragraph{Why one query costs so much.}
The datamart micro-benchmarks (\cref{tab:datamart-micro}) isolate the
aggregation on a synthetic 300-book datamart. Fetching the posting list of a
term contained in every book takes 0.60~ms, but the full search aggregation for
that term takes 26.2~ms, $43\times$ more. The cost lies in the stages after the
intersection: one \code{\$lookup} sub-pipeline per candidate book, followed by
a \code{\$facet} that counts and sorts every match. A common term has a
candidate for almost every book, so the join runs about 300 times per query.
Adding the three metadata filters makes the query \emph{slower} (37.9~ms,
$+45\%$), because the filters are evaluated per candidate inside the lookup,
after the point read by \code{\_id}, instead of pruning candidates through the
filter indexes. This reading of the query plan is an inference from the
pipeline's structure; \code{explain()} output was not recorded.

\paragraph{Memory is not the constraint, yet.}
\Cref{fig:cpu}b uses a logarithmic axis because the three processes differ by
two orders of magnitude. \code{mongod} held 348--474~MiB on average with
transient peaks up to 547~MiB (579~MiB with two replicas) during the saturated
holds, consistent with per-query sort and \code{\$facet} buffers being
allocated and released; the Search process grew from 10 to 22~MiB with
concurrency, as each in-flight request holds a goroutine stack and a response
buffer; nginx stayed at 28--31~MiB; the Indexing Service stayed below 120~MiB
(\cref{tab:indexing-resources}). The whole stack used less than 0.7~GiB of the
9.7~GiB available. The thread counts reflect the two concurrency models of
\cref{sec:replicas-threads}: \code{mongod} grew from about 45 to 155 threads (209
in the two-replica run) as connections were opened, one thread per connection,
while each Search process stayed at 13 to 24 operating-system threads for up to
100 concurrent requests. A 300-book datamart fits entirely in MongoDB's cache;
memory becomes relevant when the working set of posting arrays outgrows it,
which this corpus does not exercise.

\subsection{Effects of replication}
\label{sec:bench-replication}

The replica experiment (item RF~8 of the group's Stage~2 audit checklist, the
label used in \code{docker-compose.replicas.yml} and \code{deploy/nginx/nginx.conf})
repeated the identical k6 profile, with the same seed, datamart, host and
proxy, once with one and once with two Search replicas behind nginx; the
replica count was the only variable (\cref{fig:replication}).

\begin{figure}[tbp]
  \centering
  \includegraphics[width=\textwidth]{fig4_replication}
  \caption{One versus two Search replicas behind nginx (\code{least\_conn}),
  identical k6 profile, seed, datamart and host. (a)~Throughput and (b)~95th
  percentile latency: the thin dark line of the two-replica run lies inside the
  thick light line of the one-replica run at every level. (c)~Relative change
  with two replicas; the shaded $\pm 5\%$ band is a visual reference, not a
  measured confidence interval (each configuration was run once). No change has
  a consistent sign.}
  \label{fig:replication}
\end{figure}

\paragraph{The load was distributed.}
nginx split the work evenly: from 10 clients upwards the two replicas used the
same CPU within 7\% (0.132/0.127, 0.144/0.153 and 0.137/0.138 cores at 10, 50
and 100 clients), and the \code{X-Upstream} header alternated between the two
container addresses. Their combined CPU (0.26--0.30 cores) is what one replica
used alone (0.22--0.27 cores): the work was divided between two processes, not
reduced.

\paragraph{Throughput and latency did not change.}
Throughput changed by $+4.0\%$, $-0.2\%$, $-1.8\%$ and $-0.8\%$ at 1, 10, 50 and 100
clients, and the 95th percentile by $-4.6\%$, $+1.1\%$, $+3.1\%$ and $+1.0\%$
(\cref{fig:replication}c). Every difference lies within $\pm 5\%$, the sign flips
between levels, and the one-client run, where two replicas look best, is the
level at which no replica is busy. With one run per configuration these
differences are indistinguishable from run-to-run variation, so no effect of
replication is detectable; \code{mongod}'s CPU changed by less than 1\% at
every level.

\paragraph{Why it could not change.}
The asymptotic bound explains the null result quantitatively. $X_{\max} = m /
D_{\text{cpu}}$ depends on the processors of the host and on the CPU one query
consumes; a second Search replica changes neither, because it only splits the
Search share of $D_{\text{cpu}}$, 1.1 of 45.2 core-ms, between two processes.
Even if the Search and nginx tiers cost nothing at all, the bound would rise
from 265 to 274~req/s, $+3\%$: that is the most any amount of Search
replication can buy on this host. Replication did change one property of the
datamart: each replica brings its own connection pool, so \code{mongod} ran up to
209 threads instead of 155, with no more CPU to run them. On one host,
replicating the stateless tier buys availability (nginx routes around a replica
that cannot be reached), not throughput. It raises throughput only when the
replicated tier is the bottleneck, or when the replicas run on separate machines
together with a datamart that scales out as well (\cref{sec:stage3}).

\paragraph{CPU-bound work scales, up to the physical cores.}
The three text functions run in parallel without shared state and reach
$3.4\times$ to $4.6\times$ with eight threads (\cref{tab:micro},
\cref{fig:threads}a). Scaling is close to linear up to two threads and flattens
beyond four, as expected on six physical cores with simultaneous
multithreading, the same effect that doubles the cost of a query in
\cref{sec:bench-resources}. \code{ProcessText}, the tokeniser, scales least: it
allocates about 15~MB per book, so memory bandwidth and garbage collection are
plausible further limits. Threads are therefore \emph{not} what limits indexing:
the CPU-bound share of an update (13.7~ms) already parallelises, and the write
to MongoDB dominates (\cref{sec:bench-indexing}).

\paragraph{Datamart-bound work does not scale with client threads.}
The datamart micro-benchmarks were swept with \code{-cpu 1,2,4,8}; their
speed-ups stay between 0.89 and 1.01 (\cref{fig:threads}b), and, for example,
\code{SearchBooksWithoutFilters} takes 26.22--26.32~ms at every setting. These
benchmarks issue one request at a time, so the sweep varies the client's thread
count, not the load on the server. The flat result shows that the cost of a
datamart operation is spent in \code{mongod}, not in the Go client; how the
server scales with concurrent requests is what the k6 runs measure.

\paragraph{Network-bound work scales almost linearly.}
Ingestion scales almost linearly up to four download workers ($3.51\times$) and
reaches $5.42\times$ (21.3~books/s) at eight, with the Ingestion process using
on average less than 2\% of the machine's CPU (\cref{tab:ingestion}). Its limit
is the latency of the upstream Gutenberg server, not local resources. This
experiment ran on a different machine and network from the official session,
so its absolute rates are not comparable with the other results; the shape of
the curve is the finding.

\subsection{Coordination overhead}
\label{sec:bench-coordination}

The Control Module logs the wall-clock duration of every ingestion and
indexing step it waits for. The time of a run that is \emph{not} spent waiting
on a service step, its worker time minus the step totals, is therefore an upper
bound on the orchestrator's own overhead: claiming, recording progress under
\code{flock}, logging and retry backoff. \Cref{tab:coordination-runs} reports
four runs of 100 books with 1, 2, 4 and 8 workers. These runs predate the
official session and used different ID ranges, so they are reported as a table
of indicative values rather than plotted next to the official curves.

The orchestrator itself is cheap: in the run without failures, at most 2.6\% of
worker time was spent outside service calls, and that bound also includes the
idle tail at the end of the run. The higher shares at one and two workers come
from retry backoff: those runs predate the realignment of the ingestion entry

answered with \code{503} and retried as transient before being recorded as
failed (22 such books in the two-worker run). The real coordination cost is the
waiting. Going from one to eight workers raised end-to-end throughput only
$2.5\times$ (0.44 to 1.10~books/s), because the mean index step grew
$4.7\times$ (1.41 to 6.65~s), the same datamart contention that
\cref{fig:indexing}b measures as a rising per-book cost, while the mean
ingestion step stayed between 0.43 and 0.59~s. In other words, adding workers
to the coordinator moves the queue from the coordinator into MongoDB; it does
not shorten it.

\subsection{Bottlenecks and performance limits of the single host}
\label{sec:bench-limits}

The figures rank the limits of the deployment in the order in which they bind:

\begin{enumerate}
  \item \textbf{Search: datamart CPU, at about six concurrent clients.} One
  query costs 21~ms of one core when alone and 44~core-ms of \code{mongod} CPU at
  saturation; the bounds place the knee at $N^{*} \approx 5.6$ clients and the
  ceiling at about 250~req/s, reached with only 10 clients
  (\cref{fig:search,fig:cpu}). The Search replicas, nginx and the Go code are
  far from their limits (about 1.4~ms of CPU per query together).
  \item \textbf{Host CPU, counted in physical cores.} From 50 clients the
  containers use 94\% of the 12 logical CPUs, but the doubling of the cost per
  query shows that the six physical cores are the real capacity for
  aggregation-heavy work.
  \item \textbf{Indexing: write contention inside the datamart, not capacity.}
  Throughput reaches 5.33~books/s at ten concurrent updates with 48\%
  efficiency while the host is only 68\% busy; the per-book cost in
  \code{mongod} grows by 58\% (\cref{fig:indexing}).
  \item \textbf{Ingestion: the upstream network.} Downloads are latency-bound
  and parallelise well; local CPU and memory are negligible (\cref{fig:threads}b).
  \item \textbf{Memory: not yet a limit.} The whole stack used under 0.7~GiB of
  the 9.7~GiB available (\cref{fig:cpu}b). The posting arrays and MongoDB's cache
  grow with the corpus, which a 300-book datamart does not exercise.
  \item \textbf{Coordination: not a throughput limit.} The orchestrator accounts
  for at most 2.6\% of worker time; its cost is waiting on the datamart.
  \item \textbf{Co-location.} Load generator, datamart and services share the
  same CPU, so the measured ceiling is a property of the whole host, not of
  any single service.
\end{enumerate}

If the datamart scaled out, the next limit on the read path would be the Search
tier itself, at about 1~ms of CPU per query, or roughly 1{,}000 queries per
second per core. That figure is an extrapolation from the measured cost, not a
measurement; it is also the point at which Search replicas would start to pay
off.

\subsection{Threats to validity}
\label{sec:validity}

\begin{itemize}
  \item \textbf{One run per configuration.} The k6 results have no
  run-to-run confidence intervals; differences of a few percent, such as those
  between one and two replicas, cannot be distinguished from noise.
  \item \textbf{Short holds.} The 30~s hold phases capture steady state but
  not long-run effects such as cache eviction or the growth of the WiredTiger
  cache.
  \item \textbf{Co-located load generator.} k6 competed with the services for
  CPU, especially at 100 VUs, and its own consumption was not sampled.
  \item \textbf{Sampling.} \code{docker stats} yields one sample about every
  3~s, each covering a short interval, so the per-level CPU values are means
  of 8 to 10 samples. During the saturated holds the coefficient of variation
  of \code{mongod}'s CPU stayed below 2.5\%; the small Search and nginx
  readings vary more (up to about 30\%), which is why their per-query costs are
  quoted to one significant digit.
  \item \textbf{Virtualisation and power management.} WSL2 adds a hypervisor
  layer, and CPU frequency was neither fixed nor recorded; the simultaneous
  multithreading explanation of \cref{sec:bench-resources} rests on that
  missing measurement.
  \item \textbf{Warm caches.} The page cache and MongoDB's cache were warm,
  and the indexing benchmark re-indexed books already present.
  \item \textbf{Corpus.} The search datamart was seeded by walking Gutenberg
  IDs upwards from 1 until 300 books were published; results may shift on a
  corpus with a different term distribution or size.
  \item \textbf{Unrecorded internals.} MongoDB's \code{serverStatus} counters
  and \code{explain()} plans were not captured; attributions to write conflicts
  and to the lookup stage are inferences.
  \item \textbf{Heterogeneous evidence.} The ingestion experiment ran on
  another machine, the coordination runs before the official session, and the
  API validation against MongoDB~8.3.7; these results are never compared
  numerically with the official ones.
\end{itemize}

\section{Conclusions and Future Improvements}
\label{sec:conclusions}

Stage~2 met its objectives: the Stage~1 data layer now runs as cooperating
services with documented and validated contracts, an explicit coordination
mechanism and a measured performance envelope. The measurements also answer
the question Stage~1 left open. MongoDB does serve several independent
processes correctly under concurrent access, and on a single host it is the
first component to saturate: it consumes 94--97\% of the CPU of every query
(\cref{fig:cpu}c) and all of the growth in the cost of indexing a book under
concurrency (\cref{fig:indexing}b). The design of Stage~3 follows from that
single fact.

\subsection{Strengths}
\label{sec:strengths}

\begin{itemize}
  \item \textbf{Contracts that are specified and verified.} The OpenAPI
  documents are generated from the code. The running stack passes all 19 API
  checks and 365 automated tests, both end-to-end scripts pass, and the
  pagination contract held for all 65{,}950 queries of the load tests.
  \item \textbf{Coordination that tolerates failures.} Ingestion before
  indexing is enforced twice, partially indexed books are invisible, rebuilds
  are serialised across replicas (verified live: \code{409}, then a successful
  retry), and every operation is idempotent, so a crash between a completed
  call and its record costs a replay, never a duplicate.
  \item \textbf{Graceful saturation.} Past the knee, throughput stays on its
  plateau and latency grows exactly as queueing predicts (within 2\% of
  Little's law, 6--7\% above the asymptotic bound): no request failed with 100
  concurrent clients, and overload turns into waiting, not into errors or
  collapse (\cref{fig:search}).
  \item \textbf{A lean service tier.} A Search replica needs about 1~ms of CPU
  and less than 23~MiB of memory per process, and nginx under 0.1 cores at
  250~req/s (\cref{fig:cpu}). The Go services are not where the cost is.
  \item \textbf{Concurrency that is bounded and measured.} Semaphores,
  timeouts and context propagation keep overload from turning into resource
  exhaustion. CPU-bound text processing scales $3.4$--$4.6\times$ with eight
  threads, and network-bound ingestion $5.4\times$ with eight download workers
  (\cref{fig:threads}).
  \item \textbf{Reproducible evidence.} Every figure is regenerated by one
  script from committed raw files, and every plotted value is exported as a
  table (\cref{sec:provenance}).
\end{itemize}

\subsection{Weaknesses}
\label{sec:weaknesses}

\begin{itemize}
  \item \textbf{One datamart server bounds both paths.} Search saturates at
  about six concurrent clients and 250~req/s and misses the 95th-percentile
  objective at 100 clients. Indexing reaches 48\% parallel efficiency at ten
  concurrent updates. Replicating the Search tier does not help on one host
  (\cref{fig:replication}).
  \item \textbf{An expensive query plan.} The per-candidate \code{\$lookup} and
  the \code{\$facet} make a search $43\times$ more expensive than fetching its
  postings, and metadata filters make it slower rather than faster.
  \item \textbf{Write amplification and contention.} The one-document-per-term
  layout rewrites thousands of posting arrays per book, concurrent updates
  collide on the same term documents (the per-book cost grows by 58\%), and
  the arrays of common terms approach the 16~MB document ceiling as the corpus
  grows.
  \item \textbf{Per-process coordination state.} The replay list of updates
  received during a rebuild, the ingestion single-flight map and the Control
  Module's claim cursor live in memory, so they hold only for one process.
  \item \textbf{One coordinator.} New books stop entering the pipeline while
  the Control Module is down, and synchronous calls tie a worker to a slow
  index update.
  \item \textbf{Limited evidence.} The results come from single runs with a
  co-located load generator and without MongoDB's internal counters or CPU
  frequency (\cref{sec:validity}).
\end{itemize}

\paragraph{Read path: make a query cheaper before buying nodes.}
On the current plan, one six-core data node sustains about 250~req/s. Because
the bound is $X_{\max} = m / D_{\text{cpu}}$, the read capacity of a cluster can grow
in two independent ways: more processors $m$ (data nodes that serve reads) or a
smaller demand $D_{\text{cpu}}$ per query. The second is cheaper and multiplies the
first. The micro-benchmarks show where the demand goes: fetching the postings of
a common term costs 0.60~ms, the full aggregation 26.2~ms. A plan that ranks
the intersected postings and joins the metadata of the requested page only, and
that applies filters through indexed, denormalised attributes, attacks the 97\%
share of \code{mongod} directly; every halving of the 21~ms per query doubles the
ceiling of every data node. Only then is adding nodes efficient: as a rough
illustration, sustaining 1{,}000~req/s on today's plan would need at least four
such data nodes serving reads, which is an extrapolation of the bound, not a
measurement, and assumes reads spread evenly over nodes that tolerate bounded
staleness. Once the datamart scales, the Search tier, at about 1~ms of CPU per
query, becomes the next limit, and that is the point at which Search replicas on
separate nodes start to raise throughput.

\paragraph{Write path: remove the contention, then distribute it.}
\Cref{fig:indexing} shows that indexing is not starved of CPU but loses it to
concurrency: at ten clients a third of the CPU the stack consumes is overhead
compared with the single-client cost. Adding cores to one server would feed the
same collisions. The data layout has to change first: with one document per
(term, book) pair, indexing a book inserts or replaces small, independent
documents instead of rewriting shared arrays, so concurrent updates of different
books stop colliding and the 16~MB ceiling disappears. Sharding that collection
by a hashed term key spreads the writes over data nodes, and partitioning
indexing tasks by book ID across Indexing replicas keeps each book's update on
one writer. The acceptance criterion is the metric of \cref{fig:indexing}b: the
CPU cost per book must stay flat as concurrent updates increase.

\subsection{Evolution towards the Stage 3 cluster}
\label{sec:stage3}

\paragraph{Cross-machine communication.}
The HTTP/JSON contracts carry over unchanged, because every address already
comes from configuration. In Stage~3, compose DNS names are replaced by cluster
service discovery (for example Kubernetes services or Consul). Each tier gets
its own load balancer with active health checks, and timeouts and retry budgets
are recalibrated for network delay: the 21~ms service time of a lone query
leaves room for a few milliseconds of network per hop, but timeouts must be set
from the measured percentiles, not from single-host defaults. Because the
operations are idempotent, retrying over an unreliable network stays safe;
adding jitter to the backoff prevents synchronised retry storms.

\paragraph{Storage access.}
The datalake moves from a local volume to object storage (for example MinIO or
S3) or a distributed file system. ``Header written last'' becomes ``completion
marker object written last'', and local renames become conditional writes. The
control state moves from \code{flock}-protected files to the database. MongoDB
becomes a replica set of at least three nodes for availability and read
scaling, and the inverted index adopts the one-document-per-(term, book) layout
proposed in \code{docs/mongodb.md}, sharded by a hashed key so that writes
spread without hot-term skew (\cref{sec:evidence-to-design}).

\paragraph{Distribution of tasks and requests.}
Pipeline work becomes claimable tasks: either documents in a shared tasks
collection, claimed atomically with \code{findOneAndUpdate} under a lease, or
\code{BookDownloaded} and \code{BookIndexed} events in a broker, partitioned by
book ID so that the updates of one book stay ordered. Several Control instances
(or none, under choreography) can then share the work without duplicating it.
Search requests are balanced over replicas on several nodes, and read-heavy
traffic can be served by replica-set secondaries where bounded staleness is
acceptable. That makes Search replication useful at last, because the datamart
scales with it, which is precisely the condition \cref{fig:replication} shows
to be missing on one host.

\paragraph{Consistency.}
The per-book publication protocol (pending, writes, published) remains the
unit of visibility. On a replica set, the publication steps use
\code{w: majority}, so that a published book cannot be rolled back after a
failover, and search reads use \code{readConcern: majority}; the \code{-verify}
mode uses causally consistent sessions to read its own writes. Rebuild
publication switches from two \code{renameCollection} commands, which sharded
collections do not support, to versioned collections behind a single pointer
document that readers resolve once per request, which also closes the
sub-millisecond mixed window of the current swap.

\paragraph{Recovery from unavailable nodes.}
Health checks split into liveness and readiness, where readiness includes
MongoDB connectivity, so that load balancers stop routing to a replica that
cannot serve. nginx already ejects a replica after three failures for 10~s and
retries connection errors on another. Driver-level retryable reads and writes
absorb replica-set elections. Leases expire, so the work of a crashed holder is
taken over; coordinators resume from durable task state; and idempotency makes
redelivery harmless. To tolerate clock skew between nodes, lease expiry should
use the server's clock rather than the client's, and writes made under a lease
should carry a fencing token, so that a paused former holder cannot overwrite
the work of its successor.

\subsection{Prioritised improvements}
\label{sec:improvements}

The bottleneck analysis orders the work by expected impact, and each item names
the figure that will show whether it worked:

\begin{enumerate}
  \item \textbf{Make a query cheaper} (\cref{fig:search,fig:cpu}). Restructure
  the aggregation so that the join runs only for the requested page: without
  filters, sort the intersected postings by score and limit them before the
  \code{\$lookup}; with filters, evaluate them on filterable attributes
  denormalised into the postings (or in a first, index-backed query on
  \code{books}). Then add a cache of hot queries in the Search replicas, keyed
  by query, filters, page and index version, which is also what would let
  replication raise throughput. Validate each change with \code{explain()}, the
  micro-benchmarks and the k6 profile.
  \item \textbf{Remove write amplification} (\cref{fig:indexing}). Adopt the
  (term, book) layout, so that indexing a book inserts or replaces small
  documents instead of rewriting arrays, and remeasure the per-book cost of
  concurrent updates.
  \item \textbf{Strengthen the evidence.} Record \code{serverStatus} (write
  conflicts, tickets, cache), query plans and CPU frequency, run k6 from a
  separate machine, pin or limit containers so that \code{mongod}'s share can
  be controlled, and repeat every configuration at least three times so that
  the figures can carry confidence intervals.
  \item \textbf{Move coordination state into the datamart.} A tasks collection
  with leases replaces the control files and the in-memory claim, a
  prerequisite for several coordinators and for Stage~3.
  \item \textbf{Keyset pagination} (continuing after the last returned score and
  book ID) avoids the linear cost of deep offsets.
\end{enumerate}

In summary, Stage~2 delivers a correct, observable and reproducible
service-oriented search engine whose limits are known and explained: on one
machine, the shared datamart sets the ceiling at about six concurrent clients,
and adding service replicas cannot raise it. Stage~3 must therefore make each
query cheaper, scale the data tier together with the services, and replace with
cluster-wide mechanisms every local assumption that Stage~2 relied on.
